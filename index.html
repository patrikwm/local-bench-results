CLOUD EVENT LOG


  


  
MISSION

  
Can open-weight AI models, running on one gaming PC, replace a paid cloud AI subscription for real programming work?
     Every model gets the same coding tasks through two open-source terminal agents, Pi and OpenCode.
     Each task runs 3 times; a hidden test suite decides pass or fail. No judges, no vibes.


  
TEST SETUP

  

    
    
      
  • Languages (7): Python, TypeScript, Java, C#, C++, Rust, Go. Each gets 4 tasks at L1 (fix a bug ×2, add a feature, write tests) and 2 at L2 (a bug across files and a new feature in a real open-source project).
    • 
      
  • Agents: Pi 1.3.0 and OpenCode 2.0.32, both open source, pinned. Every task runs with both. They run inside a WSL sandbox with no network except the model.
    • 
      
  • Engines: Strata 0.1.44.1 (for the biggest MoE models, experts streamed from RAM) and llama.cpp b11685 (build 11685, commit 13de11e). Every result records the engine, its version, every flag, the quant and the exact model files.
    • 
      
  • Sampling: each model runs with its maker's recommended settings (temperature, top_p, top_k, penalties), copied from the model card with source and quote. The agents send no settings of their own, which would otherwise mean greedy decoding on Strata.
    • 
      
  • Grading: hidden tests in a clean copy of the repo, plus the project's own test suite at L2. Build warnings and lint (ruff, tsc, eslint, javac -Xlint, dotnet format, gofmt/go vet, clippy/rustfmt, gcc -Wall, clang-format) and scope checks are recorded too. A task counts as solved only if every hidden check passes. Failed attempts keep their partial score.
    • 
      
  • Ladder rules: a model passes a level when it solves at least half of its task-and-agent pairs, a pair counting when 2 of 3 attempts pass. It stops after two failed levels in a row. The next level is first tried with 1 attempt per task, and attempts 2–3 run only if at least 25 % solved. Runs stuck in a loop, or making requests without changing any file, are stopped early; slow runs are not.
    • 
      
  • Limits: L1 20 min per attempt, L2 45 min, L3 3 h. Up to 32K tokens per model answer.
    • 
      
  • Measured per attempt: wall time, requests, tokens read and written, cache hits, decode speed, GPU power (nvidia-smi), CPU package power (Intel RAPL), VRAM, RAM, and energy (GPU + CPU) per solved task.
    • 
      
  • Hardware: one PC: Intel i7-13700KF, 64 GB DDR5-5600, NVIDIA RTX 4080 16 GB, Windows 11 + WSL2. A MacBook Pro M1 Max 64 GB comes later, and rented GPUs after that.

WHY WE TEST THIS WAY

  

    
    
      
  • The result is what runs on this PC. The question is whether a normal gaming PC can replace a cloud subscription, so the main table is always this machine, within the time limits. A faster rented GPU could solve more tasks in 20 minutes with the same model files, which would answer a different question. If we ever rent hardware, those results get their own, labelled row.
    • 
      
  • Every attempt costs energy, so we skip the ones that cannot change a verdict. A task-and-agent pair passes when 2 of 3 attempts pass. When attempts 1 and 2 agree, attempt 3 cannot change that, so it is not run ("majority stop"). The verdict is exactly the same; the table then says 2/2, never 3/3. This saves up to a third of the attempts.
    • 
      
  • Screening first, the full measurement for the finalists. Every model first gets one attempt per task (probe); if it solves less than a quarter, the rest is skipped. Models that continue are screened with majority stop. The 4 to 6 finalists (the strongest, at least one fast or compact model, the engine comparisons, and close calls) then get 3 fresh attempts on all of L1 and L2, so their timing and energy rest on complete, unselected runs.
    • 
      
  • Each model runs as its maker intends. Sampling settings (temperature, top_p, top_k, penalties) come from the maker's model card. With no settings at all, one engine decoded greedily and models looped; a repetition penalty we chose ourselves fixed the loops but not the score. Our own settings are only ever a separate experiment.
    • 
      
  • Hard tasks are fresh and fixed in advance. L3 tasks were written after the models were frozen; their hashes are published before any model runs them, and the tasks themselves only afterwards.
    • 
      
  • Stuck runs are stopped, slow runs are not. A model that repeats itself, or keeps making requests without changing a file, is stopped early (it saves energy and changes no verdict). A slow model that is still working may use its full time.
    • 
      
  • Grading is objective and cheap. Hidden tests decide pass or fail; no AI judges. The final grading takes about 2 seconds per attempt (2 % of the time), so it stays on the PC.
    • 
      
  • What we do not claim. Related tasks (listed under the matrix) are not independent evidence. Repetitions measure consistency, not breadth. A model's 28 L1 tasks say something about these tasks, not about a whole language.
